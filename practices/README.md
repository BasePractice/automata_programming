# practices — практическая часть курса

Примеры кода к лекциям и практические проекты. Собирается вместе с лекциями
одной командой из корня репозитория:

```bash
cmake -S . -B build && cmake --build build -j
ctest --test-dir build --output-on-failure
```

## Окружение

macOS и Linux: достаточно `cmake` и системного компилятора C.

Windows — через MSYS2 (перенесено из каталога `01.Environment`):

```bash
pacman -Syuu                                    # обновить MSYS2 и перезапустить консоль
pacman -S --needed base-devel mingw-w64-x86_64-toolchain \
                   mingw-w64-x86_64-cmake git
```

Для лекции 9 нужен верификатор SPIN — сборка под Windows лежит в
`resources/spin/windows/`, исходники и свежие сборки:
<http://spinroot.com/spin/whatispin.html>. Граф пространства состояний
рисуется graphviz:

```bash
pacman -S mingw-w64-x86_64-graphviz     # MSYS2; на macOS: brew install graphviz
./pan -D > pan.dot && dot -Tpng pan.dot > pan.png
```

Работа с репозиторием и порядок сдачи — приложение курса «Система управления
версиями Git» (`lectures/src/a1-version-control`).

## Требования к коду

Полный текст требований — приложение курса «Требования к коду курса»
(`lectures/src/a2-code-style`); собирается вместе с лекциями и лежит в
комплекте рядом с ними. Ниже — то же самое в виде рабочей справки.

Весь код курса — ISO C90 без расширений и без предупреждений
(`cmake/StatecraftStrictC.cmake`). Оформление задаётся файлом `.clang-format`
в корне и проверяется скриптом `scripts/check-style.sh`:

```bash
./scripts/check-style.sh          # проверить
./scripts/check-style.sh --fix    # переформатировать
```

Нужен **clang-format 19 или новее**: версии 18 и старше сжимают завершающие
комментарии, а с 19-й они выравниваются в столбик, и один и тот же `--fix` на
разных машинах даёт разный код. Версией постарше скрипт проверку молча
пропускает — предупреждение об этом стоит читать, иначе легко считать код
проверенным, когда он не проверялся. В CI отсутствие подходящей версии —
ошибка (`--require-clang-format`), и версия ставится из PyPI, чтобы не
зависеть от того, что кладёт `apt`:

```bash
python3 -m venv .venv && .venv/bin/pip install clang-format
CLANG_FORMAT=.venv/bin/clang-format ./scripts/check-style.sh
```

### Комментарии

Публичные заголовки снабжены комментариями Doxygen. Объём минимально
необходимый: комментарий объясняет, **зачем** сущность нужна и какого
контракта от неё ждут, а не пересказывает по-русски то, что видно из кода.
Статические функции, смысл которых ясен из имени, не документируются.

```bash
./scripts/build-docs.sh    # результат — build/docs/html/index.html
cmake --build build --target docs
```

Разметку проверяет сам doxygen: в `Doxyfile` поднят `WARN_AS_ERROR`, поэтому
неверное имя в `@param`, ссылка в никуда и незакрытая группа роняют сборку
документации. Отсутствие doxygen — предупреждение, а не ошибка; в CI стоит
ключ `--strict`, где это ошибка.

Две ловушки, на которые уже наступили:

- **`@param` — либо для всех параметров функции, либо ни для одного.**
  Doxygen считает частично описанную сигнатуру ошибкой.
- **Обратная косая черта в комментарии — команда.** Регулярное выражение
  вроде `\d+` придётся заключить в `@code` … `@endcode`, иначе doxygen
  сообщит о неизвестной команде.

Форматирование (отступы, скобки, длина строки, переносы) целиком описано
в `.clang-format`, поэтому спорить о нём не нужно — достаточно прогнать
`--fix`. Остальные требования формату не поддаются и остаются предметом
ревью:

- **Именование.** Структуры, перечисления и объединения — `CamelCase` без
  подчёркиваний; переменные и функции — `under_score`.
- **Переменные.** По одной на строку; заводить по мере необходимости; имя
  отражает назначение. Односимвольные имена допустимы только для счётчиков
  циклов, коротких локальных контекстов и временных величин. Сокращений
  избегать.
- **`switch`.** Каждая ветвь `case` заканчивается `break` или `return` —
  либо комментарием, из которого видно, что проваливание намеренное.
- **Группировка.** Скобки расставляются явно (`(a && b) || c`,
  `(a + b) & c`), даже когда приоритет операций и так даёт нужный порядок.

Два документированных исключения:

- тесты пишутся на C++11 (Catch2) — студент C++-код не сдаёт;
- `12-takt`: компилятор `taktc` порождает C99, и драйвер обязан включить
  порождённый заголовок.

## Сквозной пример

Практики лекций 5 и 4 соединяются в конвейер — это тот же пример, что
разбирается в лекциях 4, 5 и 6:

```bash
05-kleene "(a|b)*abb" | 04-dfa-nfa --minimize --dot | dot -Tpng > dfa.png
```

Конструкция Томпсона даёт 14 состояний, детерминизация — 5, минимизация — 4.
Обмен идёт текстовым описанием автомата (формат описан в `common/fsm.h`),
поэтому промежуточный результат можно посмотреть глазами и поправить руками.

## Что не компилируется, но проверяется

`09-promela` — модели для внешнего верификатора SPIN: компилировать в них
нечего, а проверять есть что. Каждая модель заведена отдельным тестом
`ctest` (`09-promela-<имя>`) и прогоняется вместе с остальным практикумом;
без установленного SPIN подпроект пропускается сообщением. Те же проверки
запускаются и скриптом — он же используется в отдельном задании CI:

```bash
./scripts/check-promela.sh            # разбор всех моделей (spin -a)
./scripts/check-promela.sh --verify   # плюс сборка pan и прогон проверки
```

Ожидаемый исход модель заявляет сама строкой `verify: ok|violation|skip` в
шапке. Модель с LTL-свойствами (`ltl имя { … }`) собирается без `-DSAFETY` и
проверяется по свойству за запуск, с предположением о слабой справедливости
(`pan -a -f -N имя`), — иначе любое свойство живости нарушается тривиально:
процесс просто никогда не выполняется.
