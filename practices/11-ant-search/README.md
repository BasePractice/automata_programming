# 11-ant-search — поиск автомата для умного муравья

Практика к лекции 11, продолжение `11-cells`. Там автомат задавался вручную;
здесь он **ищется**: тропа Санта-Фе служит функцией приспособленности, а
результатом работы программы становится таблица переходов.

Тропа, прогон и готовые стратегии берутся из библиотеки практики `11-cells` —
карта тропы обязана быть одна на весь курс, иначе числа тактов в лекции и в
тестах разойдутся.

Алгоритмов поиска два, выбираются ключом `--algorithm`:

| Алгоритм | Что это |
|---|---|
| `hill` (по умолчанию) | (1 + 1)-эволюционная стратегия: один автомат, точечные мутации |
| `ep93` | эволюционное программирование по статье Angeline и Pollack (1993) |

## Метод 1: (1 + 1)-эволюционная стратегия

Простейший из работающих:

1. есть текущий автомат; его копия случайно изменяется в одном-двух местах;
2. копия прогоняется по тропе и принимается, если оказалась не хуже;
3. лучший из встреченных автоматов запоминается отдельно.

Приспособленность — пара «сколько съедено, за сколько тактов»: сначала
сравнивается еда, при равенстве — число тактов. Поэтому поиск не
останавливается, когда тропа впервые пройдена, а продолжает сокращать такты.

Равные по качеству мутации тоже принимаются (нейтральный дрейф). Без этого
поиск застревает на первом же плато, а плато здесь огромны: большинство
перестановок в таблице переходов не меняют поведения на тропе вовсе.

Полный перебор невозможен: у автомата с *n* состояниями и двумя входными
символами `(3n)^(2n)` таблиц — при *n* = 5 это около 5,8 · 10¹¹, при *n* = 6 —
около 1,2 · 10¹⁵.

## Метод 2: эволюционное программирование, EP-93

Ключ `--algorithm ep93` переключает поиск на постановку статьи
Angeline P. J., Pollack J. B. «Evolutionary Module Acquisition» (Proc. of the
2nd Annual Conf. on Evolutionary Programming, 1993) — той самой, на которую
ссылается исходный код в репозитории `c_fsm`. Постановка оттуда же, откуда
задача: тропа Санта-Фе, **200 тактов**, не более **32 состояний**.

В этот лимит не укладывается ни одна стратегия, придуманная вручную: `scan`
тратит 315 тактов. Из статьи перенесены:

- **приспособленность** — формула (4): `food + 0.01 * (1 - t / 200)`, где `t` —
  такт, на котором съедена последняя клетка;
- **мутации** — равный шанс правки состояния или перехода; при выборе
  состояния вероятность удаления по формуле (5) равна `numstates / maxstates`,
  иначе состояние добавляется; число правок — формула (6),
  `1 + round(|N(0, T) * size|)`;
- **отбор** — состязательный по Фогелю: пять состязаний на особь, популяция
  300, верхняя половина даёт по потомку;
- **заморозка модулей** — главный предмет статьи: оператор `compress`
  объявляет случайное состояние и до пяти переходов модулем, и мутации их не
  трогают; `expand` размораживает. Вероятности 10 % и 20 %, заморожено не
  более 75 % состояний и переходов. Выключается ключом `--no-compression`.

Чего в статье нет и что решено здесь: способ начальной инициализации
популяции (случайные автоматы малого размера) и точный вид «температуры» `T`
(доля несъеденной еды).

## Запуск

```bash
11-ant-search --algorithm ep93                     # постановка статьи
11-ant-search --algorithm ep93 --no-compression    # она же без заморозки
11-ant-search --states 5 --iterations 200000
11-ant-search --from scan --states 20 --grow 3000 --iterations 500000
11-ant-search --from 3.0.0.1:3.0.0.2:3.0.0.3:3.0.0.4:3.0.2.0 --states 8
```

| Ключ | Что задаёт |
|---|---|
| `--algorithm hill\|ep93` | какой алгоритм поиска |
| `--states N` | потолок числа состояний (5 у `hill`, 32 у `ep93`) |
| `--iterations N` | бюджет: мутаций у `hill`, оценённых автоматов у `ep93` |
| `--steps N` | лимит тактов на прогон (600 у `hill`, 200 у `ep93`) |
| `--seed N` | зерно датчика: поиск воспроизводится точно |
| `--grow N` | `hill`: после N неудач подряд добавлять состояние |
| `--population N` | `ep93`: размер популяции (в статье 300) |
| `--tournaments N` | `ep93`: состязаний на особь (в статье 5) |
| `--no-compression` | `ep93`: выключить заморозку модулей |
| `--from <таблица\|стратегия>` | с какого автомата начинать |
| `--quiet` | не печатать журнал улучшений |

Печатается журнал улучшений — по строке на каждый найденный автомат, лучший
предыдущего. Начало журнала для `--from scan --states 20 --grow 3000
--iterations 2000000 --seed 1`:

```
[295] 3.0.0.1:3.0.0.2:0.1.0.3:3.4.0.4:3.0.2.0
[283] 3.0.0.1:3.0.0.2:0.2.0.3:3.4.0.4:3.4.2.0
[275] 3.0.0.1:3.4.0.2:1.4.0.3:3.4.0.4:3.0.2.0
...
[153] 3.5.2.3:3.12.2.0:0.2.1.6:3.12.0.13:0.13.2.1:3.9.2.10:...
```

Журнал из репозитория `c_fsm`, который приводит лекция 11
(315 → 295 → … → 181 такт), — другой прогон того же метода: настройки, при
которых он получен, не сохранились, поэтому воспроизводятся только сами
автоматы, а не путь к ним.

Формат записи — тот же, что понимает `11-cells trail`, поэтому найденный
автомат можно сразу прогнать и посмотреть на поле:

```bash
11-cells trail 3.0.0.1:3.0.0.2:3.0.0.3:3.0.0.4:3.0.2.0
```

## Умный муравей в терминале

`11-ant-search-tui` — прогон автомата по тропе такт за тактом, каталог
готовых автоматов и поиск прямо на экране. Цель необязательная, как и
терминальная «Жизнь» практики 11-cells: обе используют общий терминальный
слой `tui_term` (POSIX, termios и ANSI).

```bash
cmake -S . -B build -DSTATECRAFT_BUILD_TUI=ON
cmake --build build --target 11-ant-search-tui
./build/practices/11-ant-search/11-ant-search-tui
```

Цвета поля: серым — тропа, красным — еда, жёлтым — пройденный путь,
голубым — муравей. Тёмная подложка показывает поле 32 × 32: за его краем
тор замыкается.

| Клавиша | Действие |
|---|---|
| `p` (или пробел) | пауза и пуск; в конце прогона — пуск с начала |
| `→` / `←` | такт вперёд / назад (возврат точный, к любому такту) |
| `b` / `e` | к началу / к концу прогона |
| `+` / `-` | прогон быстрее / медленнее (от 5 до 320 мс на такт) |
| `↑` / `↓` | клетка крупнее / мельче, наименьшая — один пиксель |
| `r` | случайный автомат из 3–8 состояний |
| `o` | каталог готовых автоматов |
| `s` | поиск: выбор режима, остановка идущего поиска |
| `Enter` / `n` | принять найденный автомат / отклонить и искать дальше |
| `a` | принимать найденное без вопросов |
| `]` / `[` | поиск быстрее / медленнее: от 100 до 50 000 оценок за кадр |
| `q` | выход |

**Таблица автомата** — внизу, синим, в мнемонике: `q3 ●Ш0 ○П4` читается
«в состоянии 3, видя еду, шагни и перейди в 0; не видя — повернись
направо и перейди в 4». `Ш` — шаг, `Л` — налево, `П` — направо, `●` — еда
впереди, `○` — пусто. Состояние, по которому муравей действует сейчас,
выделено инверсией. **Жёлтым** подсвечены переходы, изменившиеся при
последнем шаге эволюции: у показанного автомата — относительно
предыдущего, у кандидата — относительно показанного. Новые состояния
выделены целиком.

**Каталог** (`o`), 27 автоматов:

- три придуманных вручную: «осмотр» (42 из 89), «проба» (59), «сканер»
  (315 тактов) — с последнего начинается поиск;
- все 22 записи журнала поиска от `scan` (315 → 295 → … → 153 такта; 5 → 20
  состояний);
- автомат из `c_fsm` (181 такт) и автомат, найденный с нуля на пяти
  состояниях (275 тактов).

Журнал — прогон этой же практики:

```bash
11-ant-search --from scan --states 20 --grow 3000 --iterations 2000000 --seed 1
```

Тест прогоняет каждую запись каталога и сверяет число тактов из названия с
прогоном.

**Поиск** (`s`) идёт кусками между кадрами, и экран при этом не замирает:

- (1+1)-ЭС от автомата на экране;
- (1+1)-ЭС от `scan`;
- (1+1)-ЭС с нуля на 5 и на 12 состояниях;
- EP93 в постановке статьи, с заморозкой модулей и без неё.

Каждое улучшение останавливает поиск и показывается кандидатом: внизу его
таблица с подсветкой изменений и число изменённых переходов. `Enter` делает
кандидата новым поколением: автомат встаёт на тропу и проходит её с начала.
`n` отклоняет кандидата, и поиск продолжается. С `a` подтверждать не нужно,
а `]` ускоряет сам поиск. Строка поиска показывает число оценок,
улучшений, лучший результат, число принятых поколений и зерно. Найденное
воспроизводится командой `11-ant-search` с тем же зерном.

Деление поиска на куски результата не меняет. `ant_search_run` устроен как
`ant_search_begin` + `ant_search_advance` без предела, и тест сверяет поиск
кусками по 777 оценок с поиском целиком для обоих алгоритмов: тот же
автомат, те же счётчики.

Логика программы — в `ant_session.[ch]`, тесты — в `ant_session_tests.cpp`:
пошаговый прогон и возврат, каталог, сравнение автоматов, мнемоника,
режимы поиска. Сам прогон по тактам (`ant_walk_step` в `11-cells/ant_trail.c`)
— тот же код, которым считает `ant_trail_run`, поэтому картинка не может
разойтись с числами в тестах.

## Что получается

Ориентиры, полученные на этой практике (все прогоны воспроизводятся по зерну):

| Условия | Результат |
|---|---|
| 5 состояний, 200 000 итераций, зёрна 1–10 | тропа пройдена при 7 зёрнах из 10, за 269–275 тактов; остальные три — 63, 80 и 80 клеток из 89 |
| 12 состояний, 500 000 итераций, зёрна 1–10 | тропа пройдена при 9 зёрнах из 10, за 173–193 такта; зерно 3 — 88 из 89 |
| от `scan`, до 20 состояний, `--grow 3000`, 2 000 000 итераций, зерно 1 | 153 такта |

Неудачные зёрна — не оговорка: поиск даёт результат с вероятностью, а не
гарантированно, и это тоже часть предмета.

Таблица перемерена 17.10.2026. В прежней редакции первые две строки
расходились с программой: «75 из 89» для пяти состояний и «183, 165, 88 из
89» для двенадцати. Код поиска с тех пор не менялся, то есть числа
расходились с ним с самого начала, а вывод, сделанный из первой строки, был
неверен. Таблица сравнения алгоритмов ниже перемерена тогда же и совпала до
единицы.

Последняя строка существеннее, чем кажется: перенесённый из репозитория
[c_fsm](https://github.com/BasePractice/c_fsm) журнал поиска доходит до 181
такта на 17 состояниях, и этот автомат лежит в `11-cells` под именем
`evolved`. То есть тот же метод, запущенный с другими настройками, находит
решение лучше опубликованного — и ровно поэтому найденную таблицу нельзя
принимать за «оптимальную»: она оптимальна лишь для того, кто дольше искал.

### Сравнение алгоритмов

Одна постановка на оба метода — 32 состояния, лимит 200 тактов, бюджет в
миллион прогонов, десять зёрен. Мера — та же, что в статье: сколько автоматов
пришлось прогнать до первого, съедающего всю еду.

| Метод | Решений из 10 | Медиана прогонов | Лучший результат |
|---|---|---|---|
| `hill` | 7 | 237 504 | 151 такт |
| `ep93` с заморозкой | 10 | 171 505 | 185 тактов |
| `ep93` без заморозки | 10 | 99 669 | 197 тактов |

Воспроизводится командами вида:

```bash
11-ant-search --algorithm hill --states 32 --steps 200 --iterations 1000000 --seed 1 --quiet
11-ant-search --algorithm ep93 --seed 1 --quiet
11-ant-search --algorithm ep93 --no-compression --seed 1 --quiet
```

Читать таблицу нужно с двумя оговорками.

**Лучший результат у `hill` не значит, что он лучше.** Простой поиск не
останавливается, найдя решение, и весь бюджет сокращает такты; `ep93`
останавливается на первом решении — так поставлен эксперимент в статье. Зато
`ep93` нашёл решение при всех десяти зёрнах, а `hill` — при семи.

**Заявленного ускорения от заморозки не получилось**: медиана без заморозки
вдвое меньше. Это не опровержение статьи. В её таблице четыре прогона с
заморозкой и четыре без (ускорение 1.20–2.99), причём два прогона, не нашедшие
решения, из таблицы исключены, а сравниваются не одинаковые условия, а
отсортированные ряды — самый быстрый с самым быстрым. При таком способе
сравнения разброс между прогонами превращается в «ускорение».

Отсюда правило: у метода, дающего результат с вероятностью, сравнивают
распределения на одних и тех же условиях, а не отсортированные ряды.

Совпало же вот что: лучший автомат статьи проходит тропу за 193 такта, и наш
`ep93` при первом же зерне находит автомат ровно на 193 такта.

Второе наблюдение — про число состояний. На пяти состояниях поиск с нуля
находит решение лучше придуманного вручную `scan` (269–275 тактов против
315), но не всегда: три зерна из десяти застревают на 63–80 клетках. На
двенадцати состояниях проходят девять зёрен из десяти, а путь почти вдвое
короче (173–193 такта). Лишние состояния нужны не самому решению — оно
есть и на пяти, — а **поиску**: они дают промежуточные автоматы, через
которые мутация выбирается с плато, и место для более экономной стратегии.

## Тесты

Проверяется не «поиск что-то нашёл», а свойства, без которых результатам
верить нельзя:

| Утверждение | Как проверяется |
|---|---|
| приспособленность сначала считает еду, потом такты | прямое сравнение прогонов |
| поиск воспроизводится по зерну | два поиска подряд в одном процессе дают ту же таблицу |
| разные зёрна дают разные пути | результаты расходятся |
| журнал улучшений монотонен | каждая запись строго лучше предыдущей |
| мутации не выходят за таблицу | все переходы меньше числа состояний |
| результат совпадает с независимым прогоном | найденный автомат прогоняется заново |
| пройденная тропа поиск не останавливает | от `scan` результат становится меньше 315 тактов |
| негодные настройки отвергаются | нулевой лимит, потолок состояний, автомат больше потолка |
| постановка статьи задана верно | 200 тактов, 32 состояния, популяция 300, пять состязаний |
| `scan` в 200 тактов не укладывается | прогон не завершён — задача действительно трудная |
| популяционный поиск находит решение | 89 из 89 в пределах 200 тактов |
| заморозка наблюдаема | с ней сжатия происходят, без неё — ни одного |
| удаление состояний не рвёт таблицу | все переходы меньше числа состояний |

## Чем это отличается от исходного кода

Модуль `clever_ant_gen` репозитория `c_fsm` перенесён не как есть — при
разборе (17.08.2026) в нём нашлись дефекты, которые в учебный код тащить
нельзя:

- **всё состояние поиска было глобальным**, поэтому два прогона подряд в
  одном процессе невозможны — и тестировать было нечем. Здесь состояние
  датчика и автоматы живут в структурах, передаваемых по указателю;
- **не было лимита шагов** у прогона муравья: цикл `while (apples > 0)` не
  завершался, если автомат не съедал всё, а счётчик шагов типа `uint16_t`
  молча переполнялся. Здесь лимит — обязательный параметр прогона;
- **число яблок задавалось дважды** (константой и локальной переменной) — при
  правке карты они разошлись бы. Здесь еда считается по самой карте
  (`ant_trail_food_total`), а тест сверяет результат с каноническими 89;
- **`assert(false)` вместо `return`** в разборе направления: в Release
  `assert` исчезает вместе с `NDEBUG`, и функция молча возвращала `false`.
